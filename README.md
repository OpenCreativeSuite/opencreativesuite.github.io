# Open Creative Suite website

The product site for **Open Creative Suite**: [PixelDotNet](https://github.com/OpenCreativeSuite/PixelDotNet), [VectorDotNet](https://github.com/OpenCreativeSuite/VectorDotNet) and [Hieroglyph.NET](https://github.com/OpenCreativeSuite/HieroglyphDotNet).

The site is a **Donkeh WebAssembly application**. It is built with real components and pages, uses the framework's `AppRouter`/`AppRoutes` routing, and publishes to `builds/wasm` as a static site.

## Requirements

- **.NET SDK 10**.
- A **Donkeh framework checkout** containing `Build/Donkeh.props` and `Build/Donkeh.targets`.

The project resolves the framework in this order:

1. `-p:DonkehRoot=<path>` on the command line.
2. The `DONKEH_ROOT` environment variable.
3. A `Donkeh/` folder beside the project.
4. The local checkout path used during development.

`Directory.Build.props` contains the resolution rules. `Directory.Build.targets` imports the framework's host wiring. The framework owns the WebAssembly entry point, SDK imports, host page fallback and publish flattening.

## Build and preview

```powershell
# compile
dotnet build

# publish the static WebAssembly site to builds/wasm
dotnet publish -c Release -f net10.0-browser

# or publish and stage the Pages folder in one step
npm run build:docs

# serve builds/wasm with SPA route fallback
node scripts/serve-wasm.mjs
```

Open <http://localhost:4174>.

The framework writes the publish output to `builds/wasm`. Any static file server that returns the correct MIME types for `.js`, `.wasm` and `.json` can host it.

For GitHub Pages, the workflow builds into `builds/wasm`, copies that output into `docs/`, and commits `docs/` back to the branch. Pages then serves the app from `/docs`. `wwwroot/404.html` catches routes without a physical file, stores the requested path and reloads the app; the app then renders the matching page or its 404 page.

## Pages and routing

`Program.cs` mounts `AppRouter` from `Donkeh.UILab.Routing`. `SiteShell` owns the route table:

| Route | Page |
| --- | --- |
| `/` | `HomePage` |
| `/about` | `AboutPage` |
| `/apps/*` | `ProductRoute`, which resolves the slug from `Router.Path` |
| anything else | `NotFoundPage` |

Navigation uses ordinary anchors, so the browser owns the URL, back/forward and deep links. `AppRouter`/`AppRoutes`/`Route` select the page from the initial path. `ProductRoute` is data-driven: adding a product to `content.json` is enough to get a route.

## Content

`content.json` is the single source of truth for:

- site name, description, links and licence text;
- each product's name, category, copy, version, release repository, platforms, formats and specs;
- home cards, hero chips, screenshots and long-form detail sections;
- footer links, the receipt and the about page's product index.

It is embedded as `OpenCreativeSuite.content.json` and deserialized by `SiteContent`.

### Adding a product

1. Add an object to `products` in `content.json`.
2. Put screenshots in `assets/img/apps/<slug>/`.
3. Add the URL to `wwwroot/sitemap.xml`.
4. Rebuild. `/apps/<slug>` works automatically.

## Styles

- `assets/css/site.css` is the full design system shared with the previous static site.
- `src/Styles/app-shell.css` maps the old `body`-level rules onto `.app-root` and `.site-shell`, centers the receipt, and fixes the mobile menu while the document is locked.

Both stylesheets are embedded and declared with `[assembly: Stylesheet(...)]` in `Program.cs`.

## Browser interop

The browser entry point in `Program.cs` is the one deliberate host-level customisation: it initializes `wwwroot/site-interop.js` before `DomHost.StartAsync`, then hands control to the framework host. Everything else — the SDK imports, host page fallback, entry-point target, publish folder and flattening — comes from `Donkeh.props`/`Donkeh.targets`.

`wwwroot/site-interop.js` provides the small pieces the browser bridge does not yet expose:

- **SVG namespace creation** — the bridge creates HTML elements; the module routes SVG tag names through `document.createElementNS`.
- **Initial location and page metadata** — title, description, Open Graph, Twitter and canonical URL.
- **Clipboard** — the code panel's copy button.
- **Platform detection** — download button labels.
- **GitHub release lookup** — version labels and download links, with session storage caching.
- **Reveal and scroll spy** — the existing `.reveal` and `[data-section]` animations.
- **404 redirect** — restores the requested path after the static-host fallback.

If Donkeh gains native support for any of these, the corresponding block can be removed.

## Legacy static site

The repository still contains the previous static generator:

- `scripts/build.mjs`, `scripts/serve.mjs`
- generated root files: `index.html`, `about.html`, `404.html`, `apps/`, `sitemap.xml`, `robots.txt`
- `package.json`

The deployment workflow now publishes the Donkeh app into `docs/`, not the legacy static output. The legacy files are kept for reference and can be removed once the Donkeh site is the only target.

## Deploying to GitHub Pages

1. Set `site.url` in `content.json` and the canonical/meta URLs in `wwwroot/index.html` if the site moves.
2. Push the repository.
3. In **Settings → Pages → Build and deployment**, choose **Deploy from a branch**.
4. Select the branch and the **`/docs`** folder.

`.github/workflows/pages.yml` checks out the site and the Donkeh framework, publishes `net10.0-browser`, stages `builds/wasm` into `docs/`, and commits the result with `[skip ci]`. The workflow passes the framework checkout through `DONKEH_ROOT`, so it does not depend on the local Windows path.

`docs/.nojekyll` is published with the app, so GitHub Pages serves `_framework` files without Jekyll processing.

### What ends up in `docs/`

Only files the static host serves:

- `index.html`, `404.html`, `site-interop.js`, `robots.txt`, `sitemap.xml`, `.nojekyll`
- `assets/` — screenshots and icons
- `_framework/` — the Blazor loader, .NET runtime JS/WASM, and the per-assembly `.wasm` WebCIL containers

The staging step removes redundant `.dll` copies (the .NET 10 WebCIL runtime loads the `.wasm` assemblies), precompressed duplicates, ICU data (the site uses invariant globalization), source maps, native build inputs, and IIS/runtime-config build artifacts. The current output is about 250 files and 28 MB.
